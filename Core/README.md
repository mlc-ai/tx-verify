# Core: the model and its review guide

Start here to review what a kernel theorem means. Each numbered entry lives beside the
Lean definitions it covers. The index below is generated from those entries; it is not
a second specification.

## Reading order

### Status

All ten kernels are proved on this model: eight small kernels, the production FP16 8192 GEMM
and the FlashAttention-4 forward kernel. Each exports `correct`, `completed_execution` and
`realizable_result`. The production programs, explicit preconditions and validation summaries
are in [`Kernels/Fp16Gemm8192`](../Kernels/Fp16Gemm8192/README.md) and
[`Kernels/FlashAttn4Fwd`](../Kernels/FlashAttn4Fwd/README.md).

### Review sequence

1. `Source/`, `Isa/` and `Data/`: the program, the instruction forms, values, events and
   executions.
2. `Thread/`: what one thread does, with returned values left open.
3. The feature folders: `Float/`, `Memory/`, `Sync/`, `MBarrier/`, `Async/`, `Clc/`, `Tc/`,
   `Tmem/`.
4. `Assembly/`: how the rules combine into Consistent, Unsafe, FairRun and Correct, and the
   three EXT notes that state how far Correct carries to real hardware (Overall contracts below).
5. [Assumption/](../Assumption/): the constructors a kernel builds its own assumptions from (entries ASM-* below).
6. For a kernel, review its `Spec.lean`, the statement in `Theorem.lean`, and the kernel's own
   assumptions in its `Assumptions.lean` (with any files under its `Assumptions/`, such as a code
   template that an assumption reads as an exact function).

## How to review an entry

An entry has the fields `Statement`, `Source`, `Direction`, `Defs`, `Applies`, `Premises` and
`Effect`, and it may have a `Review` field. Each field gives the reviewer one thing to check:

| Field | What the reviewer checks with it |
| --- | --- |
| `Statement` | The meaning of the rule in one or two sentences. Check that the Lean definitions say exactly this, including every exception and case split. |
| `Source` | The cited ISA passage or modeling choice. Quotes are verbatim from PTX ISA 9.5 (checked by `Tools/check_quotes.py`), and section numbers refer to that version. Check that the passage supports the rule. |
| `Direction` | The relation between the rule and its source, from the [table below](#directions). Check the claim that the label names. |
| `Defs` | The Lean definitions of the entry. `Tests/Kernel/Contract.lean` checks that every definition of Core belongs to exactly one entry. Check these definitions against the other fields. |
| `Applies` | The range of the rule's quantifiers: the events, instructions or accesses it holds for. Compare it with the `∀` binders and the pattern-match coverage of the definitions. |
| `Premises` | Every hypothesis of the definitions. Compare it, condition by condition, with the conjuncts in the definition bodies. |
| `Effect` | Where the rule is used: a field of Consistent, a rejection in Unsafe, a local computation, event construction or a `baseCausality` edge. |
| `Review` | Optional material for reviewers only, such as the test files that exercise the rule. The reader document does not show it. |

Basic rules have nonempty `Applies`, `Premises` and `Effect` fields; the entries of `Source/`,
`Data/`, `Assumption/`, `Execution.lean` and `Correctness.lean` may omit them. Representation and
interface entries explain their encoding and assert no hardware behaviour. Every model
declaration belongs to one entry, including helpers and the assembly of rules.

Every entry and every EXT or OPEN note of `Core/` also has a `Statement` field: one or two plain
sentences that say what the rule requires of programs or executions, or what the model adopts
for an EXT note, so that it can be read without the Lean names. An entry or note may also have
a `Review` field with material for reviewers only, such as the test files that exercise the
rule. In an entry, a field continues on the following lines that start with two spaces, and free
prose after the fields starts after a blank line. Each field occurs at most once in an entry, every
field line of an entry names one of the fields above, and `Tools/contract_index.py` checks these
rules. The reader document in
[docs/core/](../docs/core/README.md) is generated from these fields and from the doc comments of
the definitions by `Tools/coredoc.py`.

Review how a rule is used: an execution constraint in Consistent, a rejection in Unsafe,
an event/value computation, or a condition on runs. In particular, review the closure in
MEM-BASE-CAUSALITY and the byte-specific cases in MEM-MODEL-CAUSALITY. Composition is part of the model being reviewed.

### Directions

These labels record the intended relationship and the claim to review:

| Direction | Meaning |
| --- | --- |
| `equal` | The entry claims to follow its cited text |
| `stricter` | The entry uses a stricter protocol; review its exact effect on executions and rejection |
| `scope` | The supported fragment or launch scope is restricted |
| `reading` | The entry relies on an interpretation or a named external fact |
| `not-conservative` | The mathematical result differs from hardware results as explained by its OPEN entry |
| `representation` | The entry defines an encoding |
| `interface` | The entry defines an extension interface |
| `trust` | A trusted fact supplies a guarantee: a kernel's own, explicitly declared assumption, or a fact about the toolchain or the launch that holds for every kernel (EXT-ISA, EXT-LAUNCH) |

The labels and references are checked for completeness; their claims are reviewed by a
person. Each EXT or OPEN note has one home beside its rule in a Lean file of `Core/`, the three
overall contracts beside CORRECT. The generated index links to these notes as well as the Lean
entries.

### Disclosure

Each EXT note ends with a sentence `Disclosed by every kernel whose statement names ...: K1,
K2.` (or `Disclosed by every kernel: ...` for a note that applies to every kernel). The
backquoted items are Lean constants, mostly instruction forms (`Op.setMaxReg`), some with one
argument condition (`Op.bra (uni := true)`), and the assumption constructors of the
positional readings. A kernel's statement names a constant when it occurs in the type of
`PTX.Kernels.<K>.correct` or in a definition under `Kernels/` reached from it: the program,
`Pre`, `Post` and the assumption list. Proofs and Core or Lemmas definitions are not followed:
the shared library proofs mention every rule of the model, so a closure through them would
attribute every reading to every kernel. A reading is therefore attributed to every program
that has one of its instruction forms, also when it matters only for some runtime values (a
descriptor's swizzling mode, a barrier count compared with the CTA size); the kernel's
`Theorem.lean` says so where that is the case. `Tools/reading_uses.py` checks that each
sentence lists exactly the kernels whose `Theorem.lean` lists the note and, with `--lean`, the
kernels whose statement satisfies the condition; `--lean --write` regenerates the lists.

## What the model says

A thread trace records its events with returned values left open. An execution contains
one finite trace per thread and a reads-from source for each ordinary read byte. There
is no global mutable memory, global step or global clock. Consistent combines the local
trace, read-value, collective, waiting, bulk-copy and Tensor Memory constraints. Unsafe combines the
fault and protocol checks and the selected assumptions' safety checks.

`baseCausality` (the base causality order of §8.9.5) is the transitive closure of program
order and the synchronizes-with edges between thread instructions. The accesses of asynchronous
operations are not thread instructions, so `baseCausality` never relates them. `AsyncFinished`
separately relates a part of an asynchronous operation to a wait that observed its completion:
an acquire wait that observed its notification (`AsyncCopy.AsyncObserved`, one relation for every
notification kind) or a group wait that covers it. `modelCausality` follows that wait by a
`baseCausality` chain to the consumer (`CompletionBefore`, which for the shared-memory reads of
`tcgen05.mma` and `tcgen05.cp` also needs a `fence.proxy.async`). This includes a later
`bar.sync` handoff to another thread. Observing a copy does not by itself publish unrelated
generic stores by its issuer.

`modelCausality` adds byte-specific cross-proxy order. Its async-to-async case uses
`AsyncChain`: direct `AsyncBefore` edges compose only through actual asynchronous
memory effects covering the same byte. Each edge retains the operation identities,
completion mode and observer scope. Issuing instructions and completion notifications
are not memory-effect join points. Observing a later commit notification does not
imply that earlier notifications have arrived. The section
[The memory layer against PTX §8.9](#the-memory-layer-against-ptx-89) maps these orders onto the
clauses of §8.9.

The four fields of Correct are:

| Field | Obligation |
| --- | --- |
| `safe` | Every consistent execution passes the safety checks |
| `progress` | Every execution maximal under counted extension is complete: every thread has exited or belongs to a canceled cluster, its asynchronous work is drained and its paired Tensor Memory requests are completed |
| `terminates` | One bound holds on the counted size of every consistent execution |
| `result` | Every final memory of every complete consistent execution satisfies Post |

Failed try_wait events are uncounted. FairRun requires eventual counted growth whenever
such an extension exists. `Correct.exits`, proved in [Lemmas/Kernel/Correct.lean](../Lemmas/Kernel/Correct.lean),
combines this contract with progress and terminates to prove that a fair run reaches
completion. FairRun retains its overall progress meaning; it does not specify a separate
fairness condition for each thread.

## Basic rules and proved consequences

Core defines the basic rules, their EXT and OPEN notes, the assumption interface and the
meaning of correctness. There
are no shared assumptions: each kernel declares its own in `Kernels/<K>/Assumptions.lean`, scoped
to the instruction forms or sites (`pc`) its proof relies on, through the hooks of ASM-INTERFACE.
The parameterized constructors live in [Assumption/](../Assumption/) and are part of the model
(entries ASM-*); their proved facts are in
[Lemmas/Assumption/Facts.lean](../Lemmas/Assumption/Facts.lean). A code template that a
kernel's assumption reads as an exact function (ASM-SEGMENT) belongs to that kernel and lives
under its `Assumptions/`. Derived sufficient conditions, composition lemmas, and protocol proofs
live in [Lemmas/](../Lemmas/), which holds only proofs that Lean checks; kernel proofs and
tactics use them. Core imports only Core and Mathlib.

To review a kernel claim, check its precondition, postcondition and assumption list,
then the definitions and contracts they rely on. Lean checks the proof derivation.
`Tests/Kernel/Statements.lean` checks the theorem statements and allows only the standard
axioms propext, Classical.choice and Quot.sound. No new primitive guarantee is introduced
by placing a proved theorem in Lemmas.

## Overall contracts

Three EXT notes apply to every kernel and state how far the conclusion `Correct` carries to real
hardware. They are in [Assembly/Correctness.lean](Assembly/Correctness.lean), beside CORRECT:

- EXT-ISA — the toolchain implements the ISA;
- EXT-LAUNCH — memory and parameters at launch, with the six launch obligations;
- EXT-IMPORT — the source is the program.
